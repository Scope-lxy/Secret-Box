# 内容列表随机与推荐顺序说明

核对日期：2026-09-17（本地源码；线上生效以部署为准）

本文记录文章列表、心笺列表和文章详情“继续阅读”的当前随机规则与服务端实现。产品层面的页面行为见[小程序端 PRD](PRD-轻读手记小程序端.md)，后台配置项见[后台 PRD](PRD-轻读手记后台.md)。

## 当前规则

| 场景 | `random` 模式 | `sequence` 模式 |
|---|---|---|
| 文章列表 | 每个用户独立维护顺序；第 1 页刷新时换一套顺序；后续分页沿用这套顺序 | 按入库顺序倒序 |
| 心笺列表 | 每个用户独立维护顺序；第 1 页刷新时换一套顺序；后续分页沿用这套顺序 | 按入库顺序倒序 |
| 文章详情“继续阅读” | 每篇文章独立生成推荐顺序，同一篇文章在 30 分钟缓存窗口内供所有用户复用；本轮最多 200 篇，每页最多 20 篇 | 不适用，继续阅读始终采用随机顺序 |

文章列表和心笺列表的排序方式仍由当前小程序的 `system.articlesSortMode` 与 `system.lettersSortMode` 控制，默认值都是 `random`。

### 文章与心笺列表

- 第 1 页请求会生成一枚新的服务端随机种子。种子按“小程序实例、内容池、内容类型、用户”隔离。登录用户使用服务端确认的账号 ID，未登录用户使用小程序已有的访客 ID。
- 用户主动下拉刷新会强制重新请求第 1 页，因此会换一套顺序。普通返回、Tab 切换和点赞等操作不会主动重排当前已显示的列表。
- 第 2 页及后续页面不需要前端携带种子。服务端在进程内为同一用户保留当前列表种子，种子会保留 2 小时，旧版小程序也能继续取得同一套顺序。
- 分享内容被置顶只影响当前页面显示位置，不改变服务端的随机顺序。下拉刷新后，页面会清除临时置顶并重新按当前排序加载。

### 文章详情“继续阅读”

- 服务端按内容池维护一枚有效期为 30 分钟的窗口种子，再将窗口种子与当前文章 ID 组合为推荐种子。打开不同文章时会分别生成顺序，不再仅从内容池共用名单中剔除当前文章；同一内容池下打开同一篇文章的用户仍复用相同顺序。推荐可以自然重叠，不要求不同文章的推荐内容完全互斥。
- 推荐从整个内容池中随机排序、排除当前正在阅读的文章，再选取最多 200 篇作为本轮列表，每页最多 20 篇。例如内容池有 5000 篇文章，从其余 4999 篇中随机选取 200 篇，最多加载 10 页；可推荐文章不足 200 篇时全部展示，加载完本轮内容后自然结束，不回到开头循环。
- 首次响应中的 `recommendationPagination.seed` 供客户端请求下一页使用。续页原样使用该种子，不再次拼接当前文章 ID；即使超过 30 分钟或排序缓存已被淘汰，内容集合不变时仍可重建原顺序。新的详情请求在窗口到期后取得新种子。客户端已经具备该续页能力，无需重新发布小程序。
- 前端按服务端返回的 `totalPages` 决定是否继续加载，并按内容 ID 去重。每页仍只返回摘要；推荐广告继续使用原来的广告位、开关、首次位置与间隔，按合并后的累计列表位置插入，跨第 100 篇和后续分页不会重置位置。
- 用户点赞、收藏、解锁状态和留言属于个人数据，推荐顺序统一不代表这些状态相同。
- 内容池新增或删除内容后，当前 ID 集合会触发一次重新排序；相同种子下存量文章的相对排名保持不变。30 分钟一致性和本轮推荐无遗漏针对内容集合未发生变化的缓存窗口。后台增删可能移动分页边界和本轮 200 篇的选择范围，客户端会过滤已显示条目，刷新详情后重新取得分页；已删除文章不会继续作为推荐返回。

## 服务端实现

实现入口是[内容服务](../admin/server/src/modules/content/content.service.js)和[内容存储](../admin/server/src/modules/content/content.store.js)。

服务端先读取内容 ID，再用“随机种子 + 内容 ID”计算稳定排序值。相同种子得到相同顺序，换种子才会换顺序。这样不依赖数据库对整行内容执行 `ORDER BY RANDOM()`，也不会因为点赞、收藏数量变化而把有数据的内容推到前面。

详情推荐使用 SHA-256 摘要的前 48 位作为排序值，避免编号相近的文章在不同种子下仍成组排列；排名相同时按文章 ID 确定先后。文章、心笺一级列表保留原有排序算法。本次调整不改变点赞、收藏等数据与随机排名无关的规则。

排序后的 ID 顺序在内存中短暂缓存。列表排序缓存有效 10 分钟，最多 256 项，超出时淘汰最早的一项。文章推荐排序缓存有效 30 分钟，最多 64 项，命中后调整为最近访问，超出时优先淘汰最久未访问的一项。缓存只存 ID 顺序和内容集合签名，不存文章正文或个人互动状态，也不预先为所有文章生成推荐。

文章推荐每次请求仍会读取当前内容池的 ID 集合以发现新增、删除；排序缓存命中时不重复计算排名。未命中时只对 ID 计算排名并排序，随后批量读取当前页最多 20 篇文章及封面。阅读完前 100 篇后仍沿用相同分页路径，不会一次性读取或传输整库正文。

以约 5000 篇文章为例，一次新的文章列表顺序需要读取约 5000 个 ID 并在内存中排序一次，返回页仍只读取当前页的内容。10 个用户同时下拉时会产生 10 次独立的排序。详情推荐中，10 个用户打开同一篇文章会复用一套顺序；首次打开 10 篇不同文章则各计算一套，后续命中缓存时复用。64 项推荐排序缓存至多保留约 32 万个 ID 位置及集合签名，避免随访问过的文章数量无限增长。

当前缓存是单个 Node.js 服务进程内存缓存，服务重启后会清空。文章和心笺一级列表未随续页传种子，重启后翻页可能重新开始一套顺序；详情推荐已有种子随续页传回，内容集合不变时可重建原顺序。重启后的新详情请求会产生新的缓存窗口。后续若采用多进程或多实例部署，需要把一级列表会话和推荐窗口种子迁移到共享缓存，当前单进程部署不需要额外组件。

## 接口与发布影响

- 现有接口路径不变：`GET /api/miniapp/articles`、`GET /api/miniapp/letters` 和 `GET /api/miniapp/articles/{contentId}/recommendations`。
- 文章与心笺列表继续使用现有 `page`、`pageSize` 参数；详情推荐继续使用返回的 `seed` 请求后续页。
- 本次机制只在 `admin/server` 生效，不修改小程序页面和请求协议。部署新的 Admin 服务并重启服务即可生效，不需要重新构建或上传小程序。

### 现有客户端的长列表边界

现有客户端已支持持续请求下一页，但 `onReachBottom` 每次都会把全部已加载推荐重新传给 `setData`，也没有回收远离可视区域的卡片。本次把每个详情列表限制为最多 200 篇，在不重新发布小程序的前提下控制累计卡片、广告节点与更新数据量。该上限由服务端执行；返回的 `total`、`totalPages` 与实际可加载数量一致，客户端按现有逻辑到末页后停止请求。

微信官方的[数据更新性能建议](https://developers.weixin.qq.com/miniprogram/dev/framework/performance/tips/runtime_setData.html)要求控制节点数量并只更新发生变化的数据。若以后需要一次连续浏览数千篇，应先优化客户端的增量更新和长列表渲染，再提高上限，并进行真机验收；这部分需要重新发布小程序。

## 验证

`admin/server/test/articles.test.js` 覆盖：不同源文章的共有候选顺序确实不同、同篇文章跨用户一致、相近文章编号在固定回归种子下能换序、30 分钟前后换序、旧种子续页、缓存淘汰后顺序恢复、不足 200 篇时完整分页、超过 200 篇时只加载本轮 200 篇且候选来自全池、每页 20 条上限、小内容池自然结束、内容池隔离，以及个人互动与文章更新不被排序缓存冻结。

测试还直接执行未修改的 `miniprogram/pages/article/article.js` 的首屏处理和触底续页逻辑，用真实后端结果连续加载到 200 篇，核对整轮不重复、第 10 页后停止请求，以及默认和自定义广告间隔在后续页面保持连续。发布前执行 `npm test` 与 `npm run verify:miniapp`；实际微信真机体验另行核验。

2026-09-17 本地验证：后端完整测试 584 项通过，小程序静态校验已通过（13 个页面）。临时数据库中放入 5000 篇模拟文章，10 篇不同源文章的推荐首屏均不同，缓存命中后各自保持原序；同一种子分 10 页取得 200 篇，无重复、排除当前文章，候选不局限于入库顺序的前 200 篇，第 11 页返回空列表。带测试封面的 200 张卡片经过真实客户端数据准备逻辑后，累计列表更新数据约为 128 KB，广告位置连续；这是本机合成数据验证，不代表微信真机渲染性能。临时数据在验证结束后已清理。

本次改动只需部署 Admin 服务；当前为本地实现，尚未部署。
